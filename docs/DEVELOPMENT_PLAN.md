## 1. 项目定位

**是什么**：一套可部署在服务器/内网的 A 股量化交易平台。多个用户（管理员/研究员/交易员）在上面完成：行情数据管理 → 策略研发与回测 → 模拟盘验证 → 经合规通道实盘 → 绩效归因与对账。

**不是什么**（边界即设计）：
- 不是对外 SaaS——不向公众提供实盘通道、策略销售或投资建议（牌照红线，见 §2.1）
- 不是高频交易系统——设计上限是分钟级/日线级 CTA 与选股策略，Tick 级撮合不在范围内
- 不碰用户资金——所有实盘订单经持牌券商通道，平台只做指令生成与记录

**成功标准**（可验证，不是"感觉做完"）：
1. 三年日线全市场回测 ≤ 30s（单机），分钟级回测可用
2. 策略代码不改一行，可从回测切换到模拟盘再到实盘（同一事件循环）
3. 两个用户并发使用（一个回测、一个查数据）互不干扰，权限隔离生效
4. 风控限流器能在触发高频认定阈值（300 笔/秒、20000 笔/日）前拦截订单
5. 每日收盘后自动完成：数据更新 → 策略定时任务 → 对账报告，全程无人值守

## 2. 业务与合规约束（开发前必读，本项目的"需求文档"）

量化平台 80% 的业务复杂度来自交易规则和合规边界，而不是代码。以下全部是平台必须建模的事实。

### 2.1 商业模式红线（定性做什么不做什么）

| 行为 | 所需资质 | 结论 |
|---|---|---|
| 向公众荐股/卖策略/收费投顾 | 证券投资咨询牌照（证监会颁发） | **禁止**。无牌属非法经营罪，2026-09 有无牌"机器人荐股"获利 3300 万、主犯获刑 7 年 9 个月的判例 |
| 代客理财/受托操盘 | 私募基金管理人登记 + 合格投资者募集 | **禁止** |
| 自建交易通道直连交易所 | 交易所会员资格 | **禁止**。实盘必须经持牌券商外接，且符合 2026-09 中证协/中基协《证券交易信息系统外部接入》规范（对接方须持牌/备案、禁止转借接口、券商季度报送与熔断机制） |
| 转发/售卖行情数据 | 数据商授权（如上证信息 Level-1/2 授权） | **禁止**。免费源数据仅限自用研究 |
| **安全区**：内部工具（数据+回测+模拟+团队协作）、向持牌机构输出私有化部署 | 无需金融牌照 | **本项目定位** |

> 对个人项目来说这意味着：多用户 = 部署实例内的团队协作（自己的两个账户、朋友的小团队），而不是注册即用的公有云服务。这个边界要在 README 和产品文案里写死。

### 2.2 程序化交易监管（2024–2026 已落地，平台功能必须支持）

- 证监会《证券市场程序化交易管理规定（试行）》2024-10-08 施行；沪深北交易所《程序化交易管理实施细则》2025-07-07 施行。
- **事前报告义务**：开展程序化交易须通过券商报告账户、资金来源、策略类型、交易软件信息等，未报告不得开展。→ 平台要有"报备信息管理"页：一键生成/导出报备所需材料。
- **高频交易认定**：单账户每秒申报+撤单合计 ≥ 300 笔，或单日合计 ≥ 20000 笔即认定为高频，触发额外报告义务和重点监控。→ 平台要有**硬性限流器**（令牌桶，账户级+策略级），默认上限远低于阈值（如 5 笔/秒、500 笔/日），超限直接拒单并告警。这是风控模块的合规需求，不是性能优化。
- 券商侧负责监控异常交易行为（瞬时申报速率异常、频繁瞬时撤单等）并留痕。→ 平台侧必须同步保留完整订单生命周期日志（下单、改单、撤单、回报、拒单），这就是审计日志模块的合规依据。

### 2.3 A 股交易规则参数表（回测撮合与实盘校验的依据）

> 含 2026-07-06 交易所规则修订。数字以交易所最新公告为准，此表需随规则变化维护。

| 规则项 | 参数 | 平台实现落点 |
|---|---|---|
| 交收制度 | 股票 T+1（当日买入不可当日卖出）；跨境/债券/货币/黄金 ETF 为 T+0 | 持仓模型需区分 `available_qty`（可用）与 `total_qty`（总量），每日清算时解冻 |
| 交易时段 | 开盘集合竞价 9:15–9:25（**9:20–9:25 不可撤单**）；连续竞价 9:30–11:30、13:00–14:57；收盘集合竞价 14:57–15:00 | 时段状态机；撤单指令需校验当前时段 |
| 盘后固定价格交易 | 科创板/创业板原有；**2026-07 起扩至沪深全部 A 股及 ETF**，15:05–15:30，以收盘价成交 | 独立时段与订单类型 `AfterHoursFix` |
| 涨跌幅 | 主板 ±10%（**ST/*ST 2026-07 起由 ±5% 放宽至 ±10%**）；创业板/科创板 ±20%（ST 同）；北交所 ±30%；可转债上市首日 +57.3%/−43.3%、次日起 ±20% | 撮合限价检查；报单价超界应为废单 |
| 申报数量 | 主板/创业板 100 股整数倍（卖出可含零股一次性申报）；**科创板 200 股起、可 1 股递增**；北交所 100 股起、可 1 股递增 | 订单校验器按 `Instrument` 元数据分支 |
| 价格档位 | 股票 0.01 元；基金 0.001 元 | 价格规范化函数 |
| 可转债 | T+0、±20%（次日起） | 作为独立 `AssetType` 建模 |
| 停牌/除权除息 | 停牌不可成交；除权除息日价格调整 | 回测数据需复权因子；撮合需停牌日掩码 |

**回测撮合必须建模的偏差来源**（少任何一个，回测结果就不可信）：
1. T+1 约束（当日买不可卖） 2. 涨跌停不可成交（一字板排队假设） 3. 停牌 4. 滑点（建议：低流动性标的万 3–万 10） 5. 费用（见 2.4） 6. 信号时点（bar t 收盘出信号 → bar t+1 执行，防未来函数） 7. 集合竞价成交假设

### 2.4 交易费用模型（2026 现行，回测默认参数）

| 项目 | 费率 | 方向 |
|---|---|---|
| 佣金 | 常见万 1–万 3（默认万 2.5），单笔最低 5 元 | 双边 |
| 印花税 | 0.05% | 仅卖出 |
| 过户费 | 0.001% | 双边 |
| 经手费+证管费 | 约 0.00541% 合计 | 双边 |
| **回测默认** | 买入成本 ≈ 佣金 + 0.00641%；卖出 ≈ 佣金 + 0.05641% + 滑点 | — |

费用参数必须可配置（每个用户的券商费率不同），回测报告需单列"费用/滑点侵蚀了多少收益"。

### 2.5 多用户业务场景与角色模型

典型工作流（这就是平台核心用户旅程）：

```
研究员：拉数据 → 写策略(Python) → 参数扫描回测 → 保存实验记录
    ↓ 提交策略版本
管理员：review 代码 → 审批上线（双人复核）
    ↓
交易员：配置实盘参数(资金/通道/风控限额) → 模拟盘试运行 N 天 → 开实盘
    ↓ 每日收盘后
系统：日终清算 → 对账(平台账本 vs 券商对账单) → 绩效归因报告 → 推送
```

角色权限（RBAC，M4 实现）：

| 角色 | 数据 | 回测 | 实盘 | 用户管理 | 审批 |
|---|---|---|---|---|---|
| Admin | ✓ | ✓ | ✓ | ✓ | ✓ |
| Researcher | ✓ | ✓ | ✗ | ✗ | ✗ |
| Trader | ✓ | ✓ | ✓（限额内） | ✗ | ✗ |
| Viewer | 只读 | ✗ | ✗ | ✗ | ✗ |

资源隔离与配额：每用户独立工作目录/数据库 schema 前缀；回测任务排队（防一人跑满 CPU）；实盘账户与策略绑定，一个策略只能绑一个账户（简化风控责任边界）。

### 2.6 与本职工作的边界

- 代码、文档、数据全部在个人仓库/个人机器，不拷贝公司代码，不使用公司内部数据和通道资源。
- 反过来，公司业务中学到的领域知识（规则、风控思路）以公开监管文件和公开资料为来源写进本项目文档，形成合规的知识链。

### 4.2 归纳出的多用户平台标配功能清单（本平台功能范围依据）

**必须（MVP→M6 覆盖）**：
1. 组织/多用户 + 角色权限（Admin/Researcher/Trader/Viewer）
2. 行情数据服务（采集、落库、查询 API、数据质量校验）
3. 回测引擎 + **实验记录管理**（每次回测的代码版本/参数/结果可追溯、可对比）
4. 任务调度（每日盘前数据更新、策略定时执行、批量参数扫描排队）
5. 模拟盘（纸面交易，实时行情驱动）
6. 实盘接入（仅经持牌券商通道 + 报备材料管理 + 高频阈值限流器）
7. 风控（事前：资金/持仓/频率/价格/自成交校验；事中：回撤/异常告警）
8. 审计日志（订单全生命周期留痕 + 用户操作日志）
9. 对账（平台账本 vs 券商对账单，日终自动核对，差异告警）
10. 策略版本管理（git-backed）

**加分（v1 之后再排）**：Jupyter 研究环境、绩效归因（Brinson/因子归因）、消息推送（微信/邮件）、算力配额、策略审批双人复核流、API 网关对外开放。

### 5.2 技术选型与理由（面试必考"为什么"）

| 决策 | 选择 | 为什么（一句话理由） |
|---|---|---|
| 核心语言 | Rust | 你的主场；事件驱动引擎的性能/内存安全需求真实存在；nautilus_trader 验证了该路线的生产可行性 |
| 策略层 | Python (pyo3) | 国内量化策略生态 100% Python，SDK 不用 Python 等于没人用；Rust 内核暴露给 Python 是双语言架构的标准解 |
| Web 框架 | axum | tokio 生态原生，类型友好；**同时是你需要补的技能**（已知短板，纳入学习任务） |
| 行情库 | ClickHouse | 列存压缩比高，K 线范围查询快 10–100x；替代方案 DolphinDB（商业）、QuestDB（JVM） |
| 业务库 | PostgreSQL | 用户/实验/订单记录是强一致关系数据，无争议 |
| 缓存/队列 | Redis | 任务队列 + 实时持仓快照；单机部署简单 |
| 前端 | Vue 3 + TS | 你已有 Vue 基础（不选 React，学习成本换功能深度） |
| 监控 | Prometheus + Grafana | 行业标配，也是你的技能补强点；Latency/订单成功率/风控拦截数是核心指标 |
| 部署 | Docker Compose（单机）→ K8s（可选） | 单机能跑的生产级优先，K8s 作为学习延伸不作为 MVP 阻塞 |

### 5.3 核心抽象设计（对标 nautilus，复用 QuantKit 经验）

1. **时钟抽象 `Clock` trait**：`LiveClock`（真实时间）/ `BacktestClock`（事件时间）。策略代码无感知，回测与实盘同路径。
2. **网关抽象 `MarketDataGateway` / `ExecutionGateway` trait**：行情与交易各自一个 trait。模拟撮合器实现 `ExecutionGateway`，PTrade/QMT 适配器也实现它。**通道政策变化时只换适配器**（这是对 miniQMT 收紧风险的架构级对冲）。
3. **事件总线**：进程内 `tokio::sync::broadcast`（QuantKit 已验证）起步；平台化后跨进程事件走 Redis Stream。
4. **订单状态机**：`Pending → Submitted → PartialFilled / Filled / Cancelled / Rejected`，状态迁移必须由回报事件驱动、落审计日志，禁止策略直接改状态。
5. **风控链（责任链模式）**：订单进入网关前过 N 个检查器：资金充足 → 持仓/T+1 → 价格档位/涨跌停 → 申报数量单位 → 频率限流（令牌桶，合规阈值见 §2.2）→ 自成交防范。任一失败即拒单+告警，全部留痕。
6. **账本（Accounting）**：复权/分红处理、`available_qty` 与 `total_qty` 分离（T+1）、费用科目拆分（佣金/印花税/过户费）。

### 5.4 数据模型（核心表，M1 定稿）

- `instrument`：证券主档（代码、板块、上市/退市日、涨跌停类型、申报单位规则、状态）
- `bar_{1d|1m}`（ClickHouse）：OHLCV + 复权因子 + 数据源标记
- `adjust_factor`：分红送转事件表
- `user / role / strategy / strategy_version`：平台模型
- `experiment`：回测记录（代码 commit hash、参数 JSON、指标、Parquet 结果路径）
- `order / fill / position_snapshot`：交易留痕
- `recon_report`：对账结果
