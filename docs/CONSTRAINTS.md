# quant-infra 开发约束基线（Constraints Baseline）

> 版本 v1.0 · 2026-10-13 · 地位：**全项目最高约束文件**，与 `DEVELOPMENT_PLAN.md`（做什么）、`ARCHITECTURE.md` / `RISK_CONTROL.md` / `MODULE_DESIGNS.md`（怎么做）并列；冲突时以本文为准。
> 修改本文 = 架构级变更：必须走 §7 变更规则，禁止静默修改。

---

## 1. 使用方式（本文件如何被"严格执行"）

1. **M0 交付物包含 §6 的 T1 强制基础设施**——没有它，本文只是愿望清单。CI 红灯即违反约束，不接受解释。
2. **每次合并代码过 §7.2 PR checklist**（T2）；每个里程碑验收过 §7.3 演示 checklist。
3. **每周 30 分钟约束回顾**（§7.4）：检查 Tier-3 约束执行情况并记录。
4. 约束分级让步原则见 §5：**质量刚性，范围弹性**——时间不够砍功能，永远不砍正确性。

## 2. 强制层级定义

| 层级 | 名称 | 含义 | 违反后果 |
|---|---|---|---|
| **T1** | 机器强制 | CI/编译/lint/测试自动检查，绕过=合不进 main | 合并被阻断，无例外 |
| **T2** | 流程强制 | checklist / DoD / 演示验收，有书面记录产物 | 不合入 / 不开下一里程碑 |
| **T3** | 纪律约束 | 写下来的规则 + 周回顾检查，机器无法自动判定 | 周回顾记录违规+根因，重复违规升级为需加基础设施的 T1/T2 |

生产级原则：**每条 T3 约束都要有"能否升级为 T1/T2"的评估**；能机器判定的绝不依赖自觉。

## 3. 约束清单

### A. 法律与合规（最高优先级，违反任意一条 = 项目重定向）

| ID | 约束 | 为什么 | 强制 |
|---|---|---|---|
| LC-01 | 平台永不包含对外荐股/投顾/策略销售/收益承诺功能；策略代码默认私有 | 无牌投顾是刑事红线（DEVELOPMENT_PLAN §2.1） | T1：路由白名单测试断言不存在相关 API；T2：PR 涉及"分享/推荐/收益"字样需说明 |
| LC-02 | 实盘订单只允许经 ExecutionGateway 的持牌券商适配器；禁止实现任何直连交易所的交易协议 | 外接新规 + 牌照边界 | T1：架构测试断言 engine 是唯一提交入口；T2：网关类 PR 评审 |
| LC-03 | 限流参数 config 硬顶 = 监管值（300 笔/秒、20000 笔/日），越顶配置启动即失败 | 高频认定的合规硬顶（RISK_CONTROL §8） | T1：启动校验单测 |
| LC-04 | 实盘账户启用前置条件 = 报备档案存在且状态非"需重新报告" | 程序化交易事前报告义务 | T1：启动检查链测试（INV-P4） |
| LC-05 | 免费源行情数据仅入自用库；不提供任何对外数据转售/转发接口 | 数据授权边界 | T1：数据出口路由白名单测试 |
| LC-06 | 不使用雇主代码/数据/内部资料；本项目技术依据仅限公开监管文件与公开资料 | 职业边界与 IP 风险 | T3：引用来源随文档记录 |
| LC-07 | 监管参数变化 30 天内更新 RISK_CONTROL §8 参数表并补回归用例 | 参数表是唯一事实源 | T2：季度合规回顾 checklist |

### B. 账本与订单正确性（错一分钱都是 bug）

| ID | 约束 | 为什么 | 强制 |
|---|---|---|---|
| AC-01 | Money/Price/Qty 全链路禁用 f64（定点 i64，core-types 封装） | 账本精度是正确性问题（ARCHITECTURE §5.5） | T1：core-types 禁浮点扫描 + 类型封装使误用编译失败 |
| AC-02 | 一切舍入只出自 `core-types::rounding`，禁止散落 round 调用 | 舍入不一致=对账永平不了 | T1：round 调用白名单扫描 |
| AC-03 | 账本流水与事件存储 append-only；任何 UPDATE/DELETE 尝试必须失败 | 审计证据链（INV-E1/A1） | T1：集成测试尝试改写必须报错（DB 权限+触发器） |
| AC-04 | 修账必须：以券商对账单为准 + 审计事件 + 双人确认（平台上线后） | 修账是最高风险操作 | T2：settlement 流程测试；开发期双人=书面自审+24h 冷却（§5 说明） |
| AC-05 | 订单状态机迁移仅由回报事件驱动；非法迁移=拒绝+告警+safe mode | INV-O1/O2 | T1：全迁移矩阵 property 测试 |
| AC-06 | client_order_id 全局唯一幂等；同 id 重复提交不产生二次成交 | 重试与恢复的安全性 | T1：网关幂等测试 |
| AC-07 | 事件存储哈希链逐日可验证；每日校验任务失败=告警 | 留痕防篡改（P3） | T1：verify_chain 测试 + 调度任务 |
| AC-08 | 引擎系 crate（engine/oms/accounting/risk/event-core/core-types）禁止直接使用 SystemTime/Instant | 确定性内核（INV-T1） | T1：源码扫描脚本 + cargo-deny |
| AC-09 | 崩溃恢复后状态与崩溃前逐字段一致（快照+重放） | INV-E2 | T1：kill-9 property 测试每次 CI 运行 |
| AC-10 | 现金余额不可为负；账本层对每笔过账做二次校验 | R3 的最后防线 | T1：账本 property/fuzz 测试 |

### C. 风控与 fail-closed

| ID | 约束 | 为什么 | 强制 |
|---|---|---|---|
| RC-01 | 策略→网关唯一路径 = 风控链 R0–R8；SDK 面无任何绕过入口 | 风控是物理结构不是过滤器 | T1：SDK 能力面恶意使用测试（MODULE_DESIGNS §10） |
| RC-02 | R0–R8 链序不可变；变更=架构变更需评审记录 | 链序是安全属性 | T2：评审记录 |
| RC-03 | 一切"放行"默认拒绝；风控/限流/日历组件故障或超时 → safe mode 拒新单 | fail-closed 是平台第一安全属性 | T1：故障注入测试（M6 验收后保持 CI 常驻） |
| RC-04 | kill switch 独立存储（Redis+文件双写）；状态不一致按"已触发"处理 | 保守取向 | T1：注入测试 |
| RC-05 | 对账零容差；存在未决差异 → 实盘禁交易直至双人销账 | 差异=未知=禁止交易 | T1：settlement 测试 |
| RC-06 | 实盘模式首次启用前置 = RISK_CONTROL §7 对抗性测试清单 13 条全过；清单更新后需重跑 | 上线门槛 | T2：发布 checklist 签字项 |
| RC-07 | 每单每检查输出 (check_id, pass, reason_code, 耗时) 入事件存储 | 留痕与可解释性 | T1：断言测试 |

### E. 工程质量

| ID | 约束 | 为什么 | 强制 |
|---|---|---|---|
| EN-01 | CI 门槛：cargo fmt --check、clippy -D warnings、cargo-deny（advisories+bans）、全测试通过才能合入 main | 生产级底线 | T1：分支保护 |
| EN-02 | 全 workspace `#![forbid(unsafe_code)]` | 本项目无 unsafe 必要 | T1：crate 属性 |
| EN-03 | 引擎路径禁 unwrap/expect/panic!（测试代码与 main 启动期配置校验除外） | panic=safe mode 可，但不应发生在正常路径 | T1：clippy unwrap_used lint + 扫描白名单 |
| EN-04 | 错误必须结构化（thiserror enum，风控拒绝必带 reason_code）；禁止裸字符串错误 | 可分类才可监控可对账 | T2：review + RC-07 断言 |
| EN-05 | 行覆盖率：核心 crate（core-types/accounting/oms/risk/event-core）≥90%，其余 ≥70% | 账本与风控代码不配"差不多测过" | T1：llvm-cov 阈值检查 |
| EN-06 | 凭据/密钥/账户信息不入代码不入日志；网关凭据 AES-GCM 加密存储 | 安全底线 | T1：gitleaks 扫描 + 日志内容断言测试 |
| EN-07 | 新增依赖需在 PR 写明理由与替代方案；deny.toml 维护黑名单 | 供应链风险 | T2：PR 描述模板必填项 |
| EN-08 | pybind/SDK 公开表面 v1 冻结：只加不改签名；破坏性变更=版本号变更+迁移说明 | 策略代码零修改是 P0 的承诺 | T2：SDK 表面 diff 检查 |
| EN-09 | Python 侧（data-platform/sdk）：ruff + mypy 必过 CI；sdk 包 mypy strict，data-platform 渐进收紧 | mypy 是零基础 Python 的编译器级安全网 | T1：CI |
| EN-10 | Python 依赖 uv lock 锁定；锁文件变更需在 PR 说明 | 可复现构建 | T2 |

### F. 开发流程（单人 + AI 协作场景专用）

| ID | 约束 | 为什么 | 强制 |
|---|---|---|---|
| PR-01 | 文档先行：实现某模块前必须精读 MODULE_DESIGNS 对应节；实现与文档冲突 → 当场改文档或开 issue，禁止静默偏离 | 文档是契约不是装饰 | T2：模块开工 checklist 首项 |
| PR-02 | 模块完成定义（DoD）= 该模块"测试要点"全部实现且通过 | 完成不许有第二种定义 | T2：里程碑验收 |
| PR-03 | **2026-10-13 修订**（用户决定项目由 AI 全权开发）：逐行解释要求不再约束用户；可解释性转移到文档层——每个合入 PR 描述含"设计要点"段，架构叙事由 docs/ 文档集承载。**2026-10-13 二次修订**（用户明确免除答辩）：里程碑不再设口头答辩，验收仅依据验收记录与 CI 证据 | 单人+AI 模式下保持代码可审计；面试叙事依托架构文档与决策记录 | T2：PR 描述必含设计要点；里程碑验收以 docs/acceptance/ 记录为准 |
| PR-04 | 禁止 --no-verify、跳过钩子；`#[ignore]` 测试必须关联 issue 且写到期日，过期未修=CI 红 | 例外必须显式且有期限 | T1：CI 检查 ignore 数量与 issue 关联 |
| PR-05 | 里程碑演示制：上一里程碑验收场景（DEVELOPMENT_PLAN §9）未演示通过，不开下一里程碑；可以砍范围，不可跳演示 | 防止"感觉做完了" | T2：演示记录（截图/录屏+数据） |
| PR-06 | 时间盒：单任务超预算 2 倍 → 停手，书面记录阻塞点，拆分或调整，禁止无限硬刚 | 全职工作之余的时间是稀缺资源 | T3：WORK_LOG 记录 |
| PR-07 | WORK_LOG 每周更新；commit 用 conventional commits 且关联模块 ID | 求职证据链 | T3：周回顾检查 |
| PR-08 | main 分支保护：CI 全绿 + PR（self-review 写清改动范围与风险）才可合入 | 唯一可部署来源 | T1：分支保护配置 |
| PR-09 | 每周 30min 约束回顾：核对 T3 约束、例外日志到期项、下周风险 | T3 的执行机制全靠它 | T3：回顾记录 |

## 4. 单人开发的补偿控制（诚实声明）

AC-04/RC-05 的"双人确认"、PR-08 的 review，在单人开发期无法字面执行。补偿控制（上线多用户后自动升级为真双人/RBAC）：

1. **书面自审**：PR 描述必须包含"改动范围 / 风险点 / 测试证据"三段，缺失=不合入。
2. **24h 冷却**：触及 B/C 类约束的改动（风控链、账本、限流参数、修账），合入前需距最后一次修改 24 小时，冷却期内重读一遍 diff。
3. **AI 互审**：允许让 AI 对该 diff 做独立对抗性 review（找反例），review 记录归档——但结论自负，AI review 不豁免任何 T1 检查。
4. 这些补偿控制本身是 T2 约束，违反同样阻断合入。

## 5. 例外与让步流程

- 现实中总有想绕过约束的时刻。**合法的绕过只有一条路**：在 §8 例外日志登记（日期/约束 ID/理由/补偿措施/**到期日**），到期自动失效；到期未恢复的例外在周回顾中按违规处理。
- 禁止口头例外、禁止"就这一次"。
- B/C/D 类约束（正确性、风控、数据可信）**不接受例外**，只接受"顺延工期"。

## 6. T1 强制基础设施清单（M0 交付物，缺失任何一项 = M0 未完成）

```
.github/workflows/ci.yml
  ├─ cargo fmt --check
  ├─ cargo clippy --workspace --all-targets -- -D warnings（含 unwrap_used 等 lint 组）
  ├─ cargo test --workspace（含 property 测试：状态机矩阵/崩溃恢复/账本不变量）
  ├─ cargo llvm-cov → 覆盖率阈值检查（EN-05）
  ├─ cargo deny check（advisories + bans）
  ├─ gitleaks scan（EN-06）
  └─ python: ruff check + mypy + pytest（EN-09/10）

scripts/lint_constraints.sh        # 约束扫描（CI 调用）
  ├─ 引擎系 crate 源码扫描：SystemTime|Instant 直接引用（AC-08）
  ├─ core-types f64/f32 扫描（AC-01）
  ├─ round( 调用白名单扫描（AC-02）

根 Cargo.toml：workspace lints 统一配置
各 crate：#![forbid(unsafe_code)]（EN-02）
GitHub：main 分支保护（EN-01/PR-08）
pre-commit：fmt + 快速 clippy（本地快速反馈，不替代 CI）
```

## 9. 约束变更规则

- 新增/修改/废止约束：本文 diff + 变更说明（为什么/影响面/新增的强制方式），在 PR 中单独可辨识。
- 每季度（LC-07 回顾时）全面复审一次：哪些 T3 该升级 T1/T2、哪些约束已过时。
- 约束只增不减为默认；废止需说明"为什么不再需要"。
